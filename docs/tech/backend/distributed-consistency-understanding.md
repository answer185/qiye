# 分布式一致理解

## 背景
### 定义
分布式一致性（Distributed Consistency）是指在分布式系统中，多个节点、服务或数据副本之间，如何保证数据状态满足预期的一致性规则。

### 产生原因
在单体应用中，如果所有数据都存储在一个数据库中，通常可以依赖数据库事务和并发控制机制保证数据正确性。

但在分布式系统中，数据可能分布在多个数据库、多个服务、多个数据副本或不同地域的数据中心。

由于：
- 网络分区：部分节点之间无法正常通信，但这些节点本身可能仍在运行。
- 网络延时：不同服务之间通过网络通信，数据更新需要经过传输和处理。
- 数据复制延时：主节点更新后，从节点需要一定时间才能同步数据。
- 并发更新：两个请求可能同时修改同一条记录
- 服务器故障及重试：分布式调用可能出现超时，但超时不一定意味着操作没有成功。
等原因。

不同节点的数据可能暂时或持续存在差异。

## 核心思想
### 强一致性与最终一致性
- 强一致性：通常要求操作完成后，后续读取不能违反该一致性模型所规定的最新状态。
- 最终一致性：允许不同副本在一段时间内存在差异，但在停止产生新更新、通信和修复机制正常等条件下，副本最终能够收敛到一致的状态。

### CAP
- C（Consistency）：一致性。CAP 语境下，通常指线性一致性。
- A（Availability）：可用性。每个到达非故障节点的请求，都能在有限时间内获得响应。
- P（Partition Tolerance）：分区容错性。网络分区发生时，系统仍能以某种方式运行。

CAP 的核心结论是：

**当网络分区实际发生时，分布式系统无法同时保证线性一致性和 CAP 意义上的完全可用性。**

系统需要根据业务要求，在分区期间选择相应的行为。

例如：
- 银行账户余额转账可能优先保证一致性，必要时拒绝部分操作。
- 某些社交信息或商品浏览功能可能允许读取旧数据，以保持较高可用性。
    

### ACID
- Atomicity：原子性。
- Consistency：一致性。
- Isolation：隔离性。 
- Durability：持久性。

用于保证数据事务的一致性。

### BASE
BASE 是分布式系统中常见的一种设计理念：

- Basically Available：基本可用。
- Soft State：允许系统状态在一定时期内变化。 
- Eventual Consistency：最终一致性。

BASE 强调在适当场景下，通过允许暂时不一致来提高系统的可用性和扩展能力。

## 技术方案
### 主从复制
主从复制是指由主节点处理写入，再将变更同步到从节点。

```
        应用服务
           |
           v
        主数据库
        /      \
       v        v
   从库 A     从库 B
```

优点：
- 可以扩展读取能力。
- 可以通过副本提高一定程度的故障恢复能力。
- 应用可以根据需求选择读取主库或从库。
    

缺点：
- 异步复制可能导致读到旧数据。
- 主从切换可能涉及数据丢失风险，具体取决于复制和故障转移机制。
- 需要处理复制延迟、故障检测和副本恢复。
    
主从复制本身不等于强一致性。是否能保证强一致性，取决于复制协议、确认策略、读取路径和故障切换机制。

### 多数派
在多副本系统中，可以通过多数派机制确定操作结果或读取有效数据。

比如有3个数据副本，则多数派的节点数量是：
```
Q = floor(N/2) + 1 
```
即有2个节点。

更新的时候，由协调者通知所有节点更新，只要返回的成功数，多于Q,则认为成功。

读取的时候，也读取N个节点，根据数值和版本来比较，返回成功的数据。

### 共识算法
共识算法用于让多个节点对某些值、操作顺序或状态变更达成一致。

常见算法包括：
- Raft。
- Paxos。
    

以 Raft 为例，集群通常通过选举产生 Leader，由 Leader 负责接收日志并复制到其他节点。

当日志满足协议规定的提交条件后，集群才能将其视为已提交的日志。

共识算法常用于：
- 分布式配置管理。
- 分布式协调服务。  
- 元数据管理。
- 具备强一致性要求的复制状态机。
- 数据库或存储系统的复制与故障切换。

### 乐观锁与版本控制
使用版本号来控制相应数据的更新，比如：
```
UPDATE inventory
SET quantity = quantity - 1,
    version = version + 1
WHERE product_id = 2001
  AND quantity >= 1
  AND version = 10;
```
如果更新影响行数为 1，说明该版本下的更新成功；如果影响行数为 0，则可能是版本已变化或库存不足，需要重新读取并判断。


### 幂等与去重
幂等是指相同操作重复执行时，不会产生超出预期的重复效果。

例如，支付服务可以使用业务请求号作为幂等键，防止同一个支付请求因网络重试而被重复处理。

常见做法包括：

- 唯一业务请求号。
- 数据库唯一约束。
- 消息消费记录。
- 版本号或状态机检查。
- 对重复请求返回之前的处理结果。

幂等不能单独保证所有分布式一致性，但它是重试和故障恢复机制的重要基础。

## 常见场景
### 相关联的业务数据
比如 订单与库存，订单创建后需要扣减或预留库存。
需要先明确业务要求：

如果订单与库存必须严格协调，可以评估 XA 或其他强一致性机制。

如果业务允许短暂不一致，可以采用库存预留、可靠消息、重试和补偿。

关键是防止超卖、重复扣减和订单状态与库存状态长期不一致。

### 缓存与数据库
应用更新数据库后，Redis 或本地缓存可能仍然保留旧数据。

常见做法包括：

1. 更新数据库。
2. 删除对应缓存。
3. 如果删除失败，进行重试或通过消息修复。
4. 对高并发场景使用版本号、过期策略或其他一致性控制机制。

数据库更新与缓存删除并不是天然的原子操作，因此需要考虑两者之间的故障窗口。

### 数据仓库与 BI
制造企业的订单系统、库存系统、生产系统可能分别向数据平台提供数据。

数据采集和处理通常存在延迟，因此数据仓库中的数据不一定与业务数据库实时一致。

常见方案包括：

- CDC（Change Data Capture）。
- 消息驱动的数据同步。
- 定时增量同步。
- 数据质量校验。 
- 对账和补数机制。

在 BI 场景中，通常应明确数据的更新时间和延迟要求，而不是一律追求强一致性。

例如，经营概览允许延迟一分钟，而财务结算指标可能需要更严格的核对与确认流程。

### 跨地域多活
跨地域系统需要同时考虑网络延迟、数据复制、写入冲突和故障切换。

如果多个地域都允许修改同一份数据，就必须定义冲突处理规则。

常见策略包括：

- 单主写入。
- 按数据分区指定写入地域。
- 基于共识协议的协调。
- 多主复制与冲突解决。

多地域部署不意味着天然具备高可用，也不意味着天然具备强一致性。需要结合网络条件和业务需求设计。

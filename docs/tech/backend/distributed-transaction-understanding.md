# 分布式事务理解
## 定义
分布式事务（Distributed Transaction）是指一个业务操作涉及多个独立的事务资源，例如多个数据库、多个微服务或多个系统，需要通过一定的机制保证这些操作满足预期的一致性要求。

## 需要解决的问题
- 多个服务的操作如何协调？
- 一个服务执行失败时，如何处理其他服务已经完成的操作？
- 网络超时后，如何判断事务的真实状态？
- 协调服务发生故障后，如何恢复未完成的事务？
- 如何在一致性、性能和可用性之间进行权衡？

## 核心角色
### 事务协调者 Coordinator
协调者负责管理全局事务，协调各个参与者完成事务。

其主要职责包括：

- 创建全局事务并分配事务 ID。
- 记录事务参与者。
- 收集参与者的执行结果。
- 决定全局事务提交或回滚。
- 持久化事务状态。
- 在故障恢复后继续处理未完成的事务。

协调者可以集成在应用中，也可以通过独立的事务协调服务提供。

### 事务参与者 Participant

参与者负责执行具体的事务操作，例如订单数据库、库存数据库。

参与者需要根据所采用的协议支持相应的事务操作。

在标准 XA 两阶段提交中，参与者需要能够执行准备、提交和回滚操作。

普通 HTTP API 返回成功，并不意味着它就具备参与标准 2PC 的能力。

### 全局事务与本地事务

全局事务（Global Transaction）是跨越多个事务资源的整体业务事务。

本地事务（Local Transaction）是在某个数据库或事务资源内部执行的事务。

例如，一个下单操作可能包含：

- 全局事务：创建订单并扣减库存。
- 订单本地事务：修改订单数据库。
- 库存本地事务：修改库存数据库。

不同分布式事务方案，协调这些本地事务的方式有所不同。

## 技术方案
### 2PC 两阶段提交
#### 定义
2PC（Two-Phase Commit）是一种经典的分布式事务协议，通过两个阶段协调多个事务参与者，使它们按照统一的全局决议提交或回滚事务。

两个阶段分别是：

1. Prepare：准备阶段。
2. Commit / Rollback：提交或回滚阶段。
    
#### XA: 基于标准接口实现
XA 是一种分布式事务规范，定义事务管理器与资源管理器之间的协作接口。

典型角色包括：

- TM（Transaction Manager）：事务管理器，负责协调全局事务。
- RM（Resource Manager）：资源管理器，负责管理事务资源，例如支持 XA 的数据库。

XA 常用于实现两阶段提交。

### TCC: 业务层面的分布式事务

TCC 分别代表：

- Try：尝试执行，预留业务资源。
- Confirm：确认执行。
- Cancel：取消操作，释放预留资源。

TCC 不要求数据库必须提供 XA 能力，但要求业务服务主动实现相应的事务接口。

### Saga: 长流程业务的分布式事务
Saga 将一个长事务拆分成多个本地事务，每个本地事务完成后独立提交。

如果后续步骤失败，则根据已经完成的步骤，执行对应的补偿事务。

例如：
```
创建订单
   |
   v
预留库存
   |
   v
处理支付
   |
   v
安排发货
```

如果支付失败，可以取消订单并释放库存。

Saga 中的补偿不是数据库意义上的回滚，而是通过新的业务操作修正之前已经提交的结果。

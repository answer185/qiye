# 服务通信理解
## 背景
微服务架构，服务之间经常需要交换请求、响应或发消息。

有以下的几类：
- 同步通信：调用方通常等待结果
- 双向或持续通信：连接可以持续存在
- 异步消息通信：发送方不必等待业务处理完成
- 底层传输协议：决定数据如何传输和组织

## 同步通信
通常有以下几种方式：
- HTTP： 是客户端与服务端交换请求和响应的协议
- REST： 围绕资源设计接口，合理使用 HTTP 方法、状态码等机制。
- GraphQL：一种 API 查询语言及运行时规范
- RPC: gRPC, 常用 Protocol Buffers 定义服务和消息结构，通常通过 HTTP/2 进行通信。

## 双向或持续通信
经常基于：WebSocket实现，建立后，可以持续双向发送消息。
```
客户端 <═══════════> 服务端
         持续连接
```
典型场景：
- 即时聊天
- 实时通知
- 在线协作
- 实时监控大屏

## 异步消息通信
基于消息队列实现：
- Apache Kafka：常用于事件流、数据集成和实时数据管道。
- RabbitMQ：常用于消息路由、任务分发和异步处理。
- Apache RocketMQ：常用于企业级消息传递和业务事件处理。

## 底层传输与协议
- TCP/UDP
- HTTP / HTTP 2
- 自定义二进制协议

## 总结

| 业务需求                   | 优先考虑                       |
| ---------------------- | -------------------------- |
| 前端查询和修改业务数据            | HTTP + REST API            |
| 前端需要灵活组合查询字段           | GraphQL                    |
| Java 微服务之间需要明确的 RPC 契约 | gRPC 或 Dubbo               |
| 需要实时双向交互               | WebSocket                  |
| 服务端向浏览器持续推送事件，但不要求双向通信 | SSE                        |
| 订单事件异步通知多个下游系统         | 消息队列                       |
| 跨系统数据同步、实时数据管道         | Kafka 等消息系统，或 CDC / 数据集成工具 |

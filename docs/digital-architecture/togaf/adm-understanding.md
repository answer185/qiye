# ADM的理解

## ADM是什么？
ADM，全称 **Architecture Development Method（架构开发方法）**，是 TOGAF 中用于开发和管理企业架构的核心方法。

## 解决的问题
它解决的核心问题是：
> 如何从企业的业务目标出发，逐步设计业务架构、应用架构、数据架构和技术架构，并将架构转化为可实施、可管理的项目计划？

## 整体结构
经典 TOGAF ADM 包含预备阶段、A 到 H 八个阶段，以及贯穿整个过程的需求管理。
```text
                    预备阶段
                       |
                       v
             A. 架构愿景
                       |
                       v
             B. 业务架构
                       |
                       v
       C. 信息系统架构（数据 + 应用）
                       |
                       v
             D. 技术架构
                       |
                       v
             E. 机会与解决方案
                       |
                       v
             F. 迁移规划
                       |
                       v
             G. 实施治理
                       |
                       v
             H. 架构变更管理
                       |
                       +------> 根据需要重新启动相关阶段

        需求管理贯穿整个 ADM 过程
```
## 各阶段详解
### 预备阶段（Preliminary Phase）
**核心问题：企业应该如何开展架构工作？**

这个阶段主要建立企业架构工作的基础，包括：

- 明确架构工作的目标和范围。 
- 确定架构团队及相关职责。 
- 建立架构治理机制。 
- 确定架构原则。 
- 选择适合企业的架构框架、方法和工具。 
- 评估企业现有的架构能力。 

例如，企业可以制定以下架构原则：

1. 业务系统之间通过明确的接口进行集成。
2. 核心业务数据应有清晰的归属。
3. 系统设计需要考虑安全性、可维护性和可扩展性。
4. 新技术的引入必须有明确的业务价值。
5. 避免为了技术先进而进行不必要的系统拆分。

**阶段产出：** 架构原则、架构治理机制、架构工作方法及组织安排。

### A 阶段：架构愿景（Architecture Vision）
**核心问题：为什么要做这个架构项目？最终希望达到什么目标？**

这是将业务诉求转化为架构项目方向的重要阶段。

主要工作包括：

- 识别利益相关者。
- 明确业务问题和业务目标。
- 确定项目范围。
- 收集高层次需求、约束和假设。
- 描述当前架构与目标架构的大致方向。
- 评估预期收益和成功指标。
- 形成架构愿景并获得关键利益相关者认可。

例如实际中经常会遇到：系统使用卡顿、旧系统扩展困难等问题。可以转成以下架构愿景：

**业务目标：**

- 提升订单、采购、生产和库存业务的协同效率。
- 改善系统稳定性和使用体验。
- 降低后续业务扩展与系统维护成本。


**架构方向：**

- 保留现有系统中仍有价值的业务能力。
- 逐步建立新的服务端架构。
- 通过统一网关管理应用接口。
- 为后续主数据、订单、采购、生产和库存等业务扩展预留空间。

**阶段产出：**
- 架构愿景文档、项目范围、关键需求、利益相关者分析和初步价值评估。

### B 阶段：业务架构（Business Architecture）
**核心问题：企业需要具备什么业务能力？业务应该如何运作？**

业务架构应该先于具体的技术设计。

主要工作包括：

- 分析业务战略和业务目标。
- 梳理业务能力。
- 梳理端到端业务流程。
- 明确组织结构、岗位和职责。
- 识别关键业务规则。
- 梳理重要业务信息和业务指标。
- 分析现状与目标之间的差距。

制造业通常围绕订单交付展开分析，常见的提高订单准时交付率的目标：

|分析对象|需要回答的问题|
|---|---|
|业务目标|如何提高订单准时交付率？|
|业务能力|企业是否具备订单管理、生产计划、采购协同和库存控制能力？|
|业务流程|从客户下单到产品交付，需要经过哪些环节？|
|组织与职责|谁负责订单确认、排产、采购和交付？|
|业务规则|什么情况下允许变更交期？如何处理缺料订单？|
|业务信息|订单、物料、库存、生产计划之间有什么关系？|
|业务指标|如何衡量准时交付率、缺料率和订单延期天数？|

业务架构的重点不是简单地罗列软件功能，而是理解企业需要什么能力，以及这些能力如何协同实现业务目标。

**阶段产出：**
- 业务能力地图、业务流程图、职责划分、业务规则清单、业务指标及差距分析。

### C 阶段：信息系统架构（Information Systems Architectures）
**核心问题：需要哪些应用和数据，才能支撑目标业务？**

C 阶段包含两个重要部分：

- 数据架构（Data Architecture）
- 应用架构（Application Architecture）

#### 据架构

数据架构主要关注：

- 企业有哪些关键业务数据。
- 数据之间有什么关系。
- 哪个系统负责维护哪类数据。
- 数据如何在系统之间流转。
- 如何保证数据质量、一致性和安全性。

#### 4.2 应用架构

应用架构主要关注：

- 企业需要哪些应用系统。
- 每个应用系统承担什么职责。
- 应用之间如何协作。
- 哪些能力应该复用。
- 哪些旧系统需要保留、改造或替换。

**阶段产出：** 
- 数据模型、数据归属及流转设计、应用清单、应用关系图、接口规划和架构差距分析。

### D 阶段：技术架构（Technology Architecture）
**核心问题：使用什么技术平台和基础设施支撑应用架构？**

技术架构关注应用运行所需的基础技术能力，例如：

- 编程语言和开发框架。
- 数据库与缓存。
- API 网关和服务发现。
- 配置管理。
- 消息队列。
- 容器化与部署平台。
- 日志、监控和告警。
- 身份认证与访问控制。
- 网络、安全和备份机制。

**阶段产出：** 
- 技术架构图、技术标准、基础设施规划、部署方案、安全及运维要求。

### E 阶段：机会与解决方案（Opportunities & Solutions）
**核心问题：如何把目标架构拆分成可实施的解决方案？**

完成业务、应用和技术架构设计后，还需要回答一个现实问题：

> 应该先做什么，后做什么？如何将目标架构转化为具体项目？

主要工作包括：

- 汇总各架构领域的差距。
- 识别可实施的解决方案。
- 将解决方案划分为工作包（Work Packages）。
- 识别不同阶段的过渡架构。
- 分析实施依赖、风险和收益。
- 确定初步实施顺序。

如某次迭代的工作包可能有：

| 工作包        | 主要内容                    |
| ---------- | ----------------------- |
| WP1：基础服务完善 | 完成 `api-system` 的必要功能   |
| WP2：网关接入   | 让前端通过统一网关访问新服务          |
| WP3：部署改造   | 完成云服务器部署、域名、HTTPS 和基础监控 |
| WP4：业务能力扩展 | 根据实际业务需求逐步建设主数据、订单等服务   |
| WP5：数据分析能力 | 在业务和数据积累到一定程度后建设 BI 能力  |

这些工作包不一定全部同时启动。应根据业务价值、实施风险和资源情况决定优先级。

**阶段产出：** 
- 解决方案组合、工作包清单、过渡架构及初步实施方案。

### F 阶段：迁移规划（Migration Planning）
**核心问题：如何从当前状态逐步走向目标状态？**

E 阶段主要识别解决方案和工作包；F 阶段进一步形成具有优先级、依赖关系和时间安排的迁移路线图。

主要工作包括：

- 对工作包进行优先级排序。
- 分析实施依赖关系。
- 评估成本、收益、风险和资源。
- 确定实施阶段及里程碑。
- 形成迁移路线图。
- 根据实际情况调整项目计划。

如上面的工作包，可能分为多个阶段落地：
- 第一阶段：完成基础能力上线
- 第二阶段：验证架构与业务价值
- 第三阶段：逐步扩展业务

**阶段产出：** 
- 迁移路线图、阶段计划、里程碑、依赖关系及资源安排。

### G 阶段：实施治理（Implementation Governance）
**核心问题：实际实施是否符合已经确定的架构？**

架构设计完成并不意味着工作结束。开发和部署过程中，实际实现可能逐渐偏离原先的架构设计。

实施治理就是通过适当的检查和决策机制，确保项目在合理范围内遵循架构原则。

主要工作包括：

- 建立架构审查机制。
- 检查关键技术和设计决策。
- 验证系统接口和业务边界。
- 检查安全、性能和运维要求。
- 处理架构偏差及例外情况。
- 记录重要的架构决策。

**阶段产出：** 
- 架构审查记录、合规性评估、架构偏差处理及实施反馈。
### H 阶段：架构变更管理（Architecture Change Management）
**核心问题：系统上线后，如何判断架构是否需要调整？**

企业业务会持续变化，架构不可能永远保持不变。

例如：

- 客户数量持续增长。
- 新增生产管理需求。
- 现有系统出现性能瓶颈。
- 新法规或安全要求出现。
- 原有技术方案维护成本过高。

这些变化可能只需要调整某个模块，也可能需要重新评估整体架构。

主要工作包括：

- 监控业务和技术环境变化。
- 收集用户反馈及运行数据。
- 评估变化对现有架构的影响。
- 判断是否需要启动新的架构迭代。
- 更新架构文档和路线图。

**阶段产出：** 
- 架构变更评估、架构更新计划及新一轮架构工作的启动依据。

### 需求管理（Requirements Management）
需求管理贯穿 ADM 的全部阶段，而不是一个只在项目开始时执行的步骤。

原因在于：业务需求会不断变化，而且不同阶段可能发现新的约束或问题。

例如：

- A 阶段发现客户最关心的是交付效率。
- B 阶段发现延期主要与缺料和计划变更有关。
- C 阶段发现订单、库存数据存在不一致。
- D 阶段发现现有部署环境无法满足可靠性要求。
- G 阶段发现实际使用方式与设计假设不同。

这些发现都可能影响后续架构和项目计划。

因此，需求管理需要持续进行需求收集、分析、优先级排序、追踪、变更和验证。

**阶段产出：** 
- 需求清单、需求优先级、需求追踪关系、变更记录及验收标准。

## 总结
现实里，不一定会完全按这个走，但是用用这个框架来思考整个架构的执行和落地，不会有遗漏。

各阶段之间的关系：

| 阶段        | 核心问题          | 主要成果           |
| --------- | ------------- | -------------- |
| 预备阶段      | 如何开展架构工作？     | 原则、治理机制、工作方法   |
| A 架构愿景    | 为什么做？要达到什么目标？ | 愿景、范围、目标与高层次需求 |
| B 业务架构    | 业务需要什么能力？     | 能力地图、流程、角色、规则  |
| C 信息系统架构  | 需要什么应用和数据？    | 数据架构、应用架构      |
| D 技术架构    | 用什么技术支撑？      | 技术平台、基础设施与标准   |
| E 机会与解决方案 | 如何把目标变成解决方案？  | 工作包、过渡架构       |
| F 迁移规划    | 先做什么、后做什么？    | 路线图、阶段计划       |
| G 实施治理    | 实施是否符合架构要求？   | 审查、合规性与偏差处理    |
| H 变更管理    | 架构何时需要调整？     | 变更评估、架构迭代      |
| 需求管理      | 如何持续管理需求？     | 需求追踪、优先级和变更记录  |

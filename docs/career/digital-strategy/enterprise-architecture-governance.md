# 企业架构的持续治理

## 背景
企业的架构成熟后，就会进入一个更长期的阶段：架构的持续治理阶段。

工作循环是：
```
             业务战略变化
                  ↓
           业务需求 / 问题
                  ↓
            架构评估
                  ↓
          架构设计 / 调整
                  ↓
          项目实施 / 落地
                  ↓
            架构治理
                  ↓
       运行数据 / 业务反馈
                  ↓
             再次评估
                  ↓
              演进
                  ↺
```

## 持续治理的内容
- 架构治理
- 需求治理
- 项目治理
- 技术债治理
- 数据治理
- 系统治理
- 架构演进
- 架构沉淀

## 架构治理
架构师需要保证架构不“跑偏”

假设最初的设计：
```
                    数据平台
                       ↑
        ┌──────────────┼──────────────┐
        │              │              │
       ERP            MES            WMS
        │              │              │
       财务           生产           仓库
```

如果没有去管，两年后可能变成：
```
ERP ──→ MES
 │       ↓
 ↓      WMS
WMS ──→ Excel
 │
 ↓
MES数据库
 │
 ↓
某个部门自己的系统

```
然后出现：
-  MES自己维护一套物料 
-  ERP又有一套物料 
-  WMS又有一套 
-  Excel还有一套 
-  某个部门自己开发了一个小系统 
这时候架构师就要做：架构偏差治理

可以建立一个文档，比如：

| 治理对象 | 问题          |
| ---- | ----------- |
| 系统   | 出现重复建设      |
| 数据   | 主数据不一致      |
| 接口   | 点对点接口过多     |
| 权限   | 权限边界混乱      |
| 技术   | 老旧技术长期存在    |
| 流程   | 系统流程与实际业务脱节 |

所以架构师并不是每天在设计新架构，而是在：
> 防止企业慢慢重新变乱。

## 需求治理
这块会占据最多的时间。各部门的人在使用过程中，都可能跑过来反馈一些问题。

架构师需要不断问为什么，了解到真实的原因后，再做统一规划。

比如：生产部门说：我们需要弄开发一个生产看板。

架构师需要问：为什么需要？

然后继续问：
```
为什么？
 ↓
现在有什么问题？
 ↓
问题造成什么损失？
 ↓
谁受到影响？
 ↓
现有系统能不能解决？
 ↓
是不是数据问题？
 ↓
是不是流程问题？
 ↓
是不是管理问题？
 ↓
真的需要开发系统吗？
```
最后可能发现：
> 根本不是需要一个新系统。
而是：
> MES的数据没有正确采集。
这就是架构治理中的需求治理。

## 项目治理
这些项目是公司每年内部可能出现的，比如：
```
ERP升级
MES建设
WMS建设
PLM建设
CRM建设
数据平台
AI项目
BI项目
设备联网
工业互联网
```

架构师需要关注：
> 这些项目是不是在朝同一个方向走？
避免各做各的，最终又形成信息孤岛。

架构师要负责：

```
战略
 ↓
企业架构
 ↓
项目组合
 ↓
系统建设
 ↓
数据建设
```
即：之后可能会参加很多项目评审。

## 技术债治理
不管是什么企业，只要用系统，随着时间推移，永远会产生技术债。
比如：
- 框架的版本变老，甚至当前版本无人维护。
- 一个接口，多年前开发，已经没人知道为什么这样设计。但又不能删。
可以维护：
> 技术债清单

| 技术债        | 风险 | 优先级 | 处理计划 |
| ---------- | -- | --: | ---- |
| 老ERP       | 高  |  P0 | 2027 |
| 老MES接口     | 中  |  P1 | 2026 |
| Oracle版本过旧 | 高  |  P0 | 2026 |
| 重复数据库      | 中  |  P1 | 2027 |
| Excel生产报表  | 中  |  P2 | 持续   |

## 数据治理
系统上线后，数据问题就会暴露出来。

架构师需要持续推动：
```
主数据
 ↓
标准
 ↓
编码
 ↓
责任人
 ↓
生命周期
 ↓
质量检查
 ↓
问题整改
```
这也是一个长期治理体系。

## 系统治理
企业的业务变化会带来架构变化。比如：
> 老板新开了工厂
就会带来应用系统上的变化。

## 架构演进
比如引入新技术，如当前的AI方向。

## 架构沉淀
不要让架构只存在某些人的脑子里，应该要建立架构资产库：
```
企业架构资产库
│
├── 业务架构
│
├── 应用架构
│
├── 数据架构
│
├── 技术架构
│
├── 集成架构
│
├── 安全架构
│
├── 主数据
│
├── 系统清单
│
├── 接口清单
│
├── 数据资产
│
├── 技术债
│
├── 项目地图
│
└── 架构原则
```
然后持续更新。

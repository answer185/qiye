# 微服务理解

## 什么是微服务
微服务架构（Microservices Architecture）是一种软件架构风格，它将一个复杂的应用系统拆分为多个相对独立的服务。

每个服务围绕特定的业务能力构建，负责自己的业务逻辑，并通过明确的接口与其他服务进行通信。

## 解决的问题
在传统单体架构中，随着业务不断发展，系统可能出现以下问题：

- 业务模块之间耦合越来越严重。
- 修改一个模块可能影响其他模块。
- 系统整体部署，局部功能也难以独立发布。
- 不同业务模块无法灵活地采用不同扩展策略。
- 多个团队共同开发时，代码和发布容易相互影响。

微服务通过划分服务边界，让不同业务能力可以相对独立地开发和演进。

例如，订单服务流量增长时，可以优先扩容订单服务，而不必同步扩容所有业务模块。

但微服务也会引入新的复杂性，包括网络通信、分布式事务、服务治理、监控、部署和故障处理。

因此，微服务不是消除复杂性，而是将部分复杂性从单体应用内部转移到分布式系统层面。

## 微服务的核心思想
包含以下4个方面：
### 按业务能力拆分
微服务的第一个问题就是如何去做服务拆分。通常围绕业务能力进行划分，而不是直接按照技术层次拆分。

例如，一个制造企业可能包括：

- 销售订单
- 库存管理
- 采购管理
- 生产管理
- 财务管理

这些业务能力具有不同的业务规则和变化频率，可以根据实际业务边界划分为不同的服务。

### 高内聚、低耦合
高内聚是指同一个服务内部的功能围绕相对集中的业务职责组织。

低耦合是指不同服务之间尽量通过明确、稳定的接口协作，避免直接依赖对方的内部实现。

例如，订单服务需要查询商品信息时，应通过商品服务提供的接口获取，而不是直接依赖商品服务的内部代码。

不过，低耦合不代表完全没有依赖。业务流程本身可能需要多个服务共同完成，关键是控制依赖关系并明确服务之间的契约。

### 服务自治
服务自治是微服务的重要思想，主要包括：

- 业务逻辑由对应服务负责。
- 服务拥有清晰的接口契约。
- 服务可以独立构建、测试和部署。
- 服务可以根据自身负载独立扩缩容。
- 服务能够管理自己的数据及其业务规则。

### 数据所有权
微服务架构中，通常由对应业务服务负责维护自己的业务数据。

例如：

- 订单服务负责订单数据。
- 库存服务负责库存数据。
- 采购服务负责采购数据。

其他服务通过 API、事件或专门的数据访问机制获取需要的信息。
这样可以减少不同服务直接修改同一份业务数据所带来的耦合。
但数据独立也会增加跨服务查询、数据同步和事务一致性的复杂度，因此需要结合业务需求设计。
## 内容及典型架构图
一个典型的微服务系统通常包括业务服务、API 网关、服务间通信、配置管理、服务治理、数据存储和可观测性设施。


```
                    用户 / 前端
                         |
                         v
                     API Gateway
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       订单服务        库存服务        商品服务
          |              |              |
          v              v              v
       订单数据库      库存数据库      商品数据库

          +--------------+--------------+
                         |
                  消息中间件
                         |
                 异步事件与业务协作

     服务发现 / 配置管理 / 监控 / 日志 / 链路追踪
```

这是一种概念架构，不意味着每个项目都必须部署所有组件。

### 业务服务
业务服务承载具体的业务能力和业务规则。

例如，订单服务负责订单创建、订单状态管理和订单查询；库存服务负责库存查询、预留和扣减。

### 网关服务
API Gateway（API 网关）是外部请求进入微服务系统的统一入口。

常见职责包括：

- 请求路由。
- 身份认证与访问控制。
- 限流。
- 请求和响应处理。
- 统一入口的监控与日志。

API 网关主要处理外部请求进入系统时的治理问题，不应将所有业务逻辑都集中在网关中。

服务之间的内部通信通常还需要独立设计。

### 服务间通信
微服务之间通常采用两类通信方式。

**同步通信：**

例如 HTTP/REST、gRPC。

调用方发出请求并等待结果，适合需要立即获得响应的场景。

优点是调用流程直观，缺点是调用链可能变长，网络超时和下游故障会影响上游服务。

**异步通信：**

例如通过 Kafka、RabbitMQ 等消息中间件传递事件。

生产者发送消息后，消费者可以独立处理，适合事件通知、异步任务和系统解耦。

异步通信需要处理消息重复、消费失败、重试、顺序和最终一致性等问题。

### 服务发现
服务发现（Service Discovery）用于解决服务实例地址动态变化的问题。

例如，订单服务需要调用库存服务，但库存服务可能有多个实例，并且实例会动态扩缩容。

服务发现机制可以帮助调用方找到可用实例。

服务发现通常包括：

- 服务注册。
- 实例健康检查。
- 服务实例查询。
- 实例上下线管理。

不同技术体系可以使用不同的实现方式，例如 Kubernetes Service、Nacos 或其他服务发现组件。

### 配置管理
微服务通常有大量配置，例如数据库地址、服务地址、超时时间和业务开关。

配置管理可以将部分配置从应用程序中分离出来，并支持统一管理和环境隔离。

配置中心并不意味着所有配置都必须远程动态更新。敏感信息仍需使用适当的密钥管理机制，关键配置变更也需要权限控制和审计。

### 可观测性
微服务的请求可能经过多个服务，因此需要建立统一的可观测性能力。

主要包括：

- Metrics：指标，例如请求量、延迟和错误率。
- Logs：日志，用于分析具体事件。
- Traces：分布式链路追踪，用于分析跨服务调用路径。

常见技术包括 Prometheus、Grafana、OpenTelemetry 和 Jaeger 等。

通过请求 ID、Trace ID 和结构化日志，可以更容易地定位跨服务故障。

## 关键的技术问题
### 分布式事务
在单体应用中，多个业务操作可能共享一个数据库事务。

在微服务中，订单和库存通常分别由不同服务管理，无法直接使用一个普通的本地数据库事务完成所有操作。

常见方案包括：

- XA / 2PC：协调多个支持相应事务协议的资源。
- TCC：通过 Try、Confirm、Cancel 协调业务资源。
- Saga：通过本地事务和补偿操作管理长流程。
- 可靠消息：通过可靠事件传递和重试实现最终一致性。

并不是所有跨服务业务都需要分布式事务。架构设计应首先确定业务一致性要求，再选择合适的方案。

### 服务容错
如果订单服务调用库存服务，而库存服务发生故障，订单服务也可能受到影响。

常见的容错机制包括：

**超时：** 为远程调用设置合理的时间上限，避免请求无限等待。

**重试：** 对适合重试的错误进行有限次数重试，并采用退避策略。重试前必须考虑操作是否幂等。

**熔断：** 当下游服务持续失败时，暂时阻止部分调用，减少故障扩散。

**限流：** 控制请求速率，防止服务过载。

**隔离：** 限制不同业务请求对线程、连接池等资源的竞争。

这些机制需要合理组合。错误地配置重试可能放大流量，熔断也不能替代业务降级和故障恢复设计。

### 数据一致性
微服务的数据通常分布在多个服务中，因此跨服务的数据状态可能短暂不一致。

例如，订单创建成功后，库存扣减事件尚未被消费。

常见的处理方式包括：

- 明确业务状态机。
- 使用可靠消息。
- 保证消息消费幂等。
- 对失败事件进行重试。
- 建立对账和补偿机制。
    
数据一致性设计的重点是明确哪些规则不能被破坏，以及系统如何在失败后恢复到合法状态。

### 服务治理
服务数量增加后，需要统一管理服务的生命周期和运行状态。

服务治理通常涉及：

- 服务注册与发现。
- 负载均衡。
- 超时和重试。
- 限流和熔断。
- 配置管理。
- 访问控制。
- 监控和告警。

这些能力可以由应用框架、网关、服务网格或其他基础设施提供。

不需要将所有治理能力都放进同一个产品，也不应该为了使用某种技术而重复建设已有能力。
## 适用场景
- 业务领域较多，边界相对清晰。
- 不同业务模块有独立的发布节奏。
- 部分模块存在明显不同的扩展需求。
- 多个团队需要并行开发和维护。
- 企业具备相应的自动化部署、监控和治理能力。

## 总结

### 优点
- **独立部署：** 一个服务可以单独发布，减少对其他服务的直接影响。
- **独立扩展：** 可以根据服务的负载情况单独扩容。
- **业务边界清晰：** 有助于将复杂系统拆分为相对独立的业务能力。
- **团队协作：** 不同团队可以围绕不同业务领域开展工作。
- **技术演进灵活：** 不同服务可以在合理的治理边界内采用不同的实现方式。

### 缺点
- **分布式系统复杂度增加：** 网络通信、超时、重试和故障恢复成为日常设计问题。
- **数据一致性更难处理：** 跨服务操作不能简单依赖一个本地事务。
- **部署和运维成本上升：** 服务数量增加会带来更多构建、部署、监控和治理工作。
- **调试困难：** 一个业务请求可能经过多个服务，需要分布式链路追踪和统一日志。
- **测试复杂度增加：** 除了单元测试，还需要考虑服务契约、集成测试和跨服务业务流程。
- **团队要求提高：** 需要具备自动化部署、可观测性、故障处理和服务治理能力。

因此，微服务并不天然比单体架构更好。

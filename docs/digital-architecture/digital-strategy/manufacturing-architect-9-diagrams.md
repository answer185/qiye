# 制造业架构师的图谱：9 种常用架构表达方式

在架构设计过程中，经常需要使用图形来表示相应的业务场景、流程、数据关系等。常用的图类型有：
- 树
- 流程图
- 泳道图
- 关系图
- 层级图
- 时序图
- 矩阵图
- 甘特图：时间线/路线图
- 象限图 / 坐标图

## 树
准确来说，树也是属于层级图里的一种，不过因为用的场景太多，所以独立出来。
可以用来表示：
### 组织架构图
在做架构设计时，需要找到合适的人，这张图用于弄清楚：
> 谁负责什么？
例如：
```
董事长
  ├── 总经理
  │    ├── 生产中心
  │    ├── 采购中心
  │    ├── 销售中心
  │    ├── 财务中心
  │    └── 人力行政
  └── 信息化/数字化中心
```

或者：
```
                    总经理
                       │
      ┌────────────────┼────────────────┐
      ↓                ↓                ↓
    销售中心          生产中心          采购中心
      │                │                │
  ┌───┴───┐       ┌────┼────┐       ┌───┴───┐
销售部   跟单部    计划部  生产部  质量部   采购部  仓储部
```

### 业务架构图
用于回答：
> 企业到底有哪些业务？

业务具体指的是：
> 企业为了创造价值、服务客户、获得收入、控制经营活动而持续开展的一组事情。

画业务架构时，并不是把所有“事情”平铺出来，而是要进行分层、归类、抽象。
例如：
```
企业经营
├── 市场与销售
├── 产品研发
├── 采购
├── 生产
├── 仓储物流
├── 质量
├── 财务
└── 人力资源
```

或者
```
                         企业经营
                            │
       ┌────────────────────┼────────────────────┐
       ↓                    ↓                    ↓
    市场销售              产品研发              供应链
       │                    │                    │
   ┌───┼───┐             ┌──┼──┐           ┌────┼────┐
   ↓   ↓   ↓             ↓  ↓  ↓           ↓    ↓    ↓
客户  报价  订单          产品 BOM 工艺      采购  仓储  供应商
                                                   │
                                                   ↓
                                                 生产
                                                   │
                                    ┌──────────────┼──────────────┐
                                    ↓              ↓              ↓
                                  计划             制造             质量
                                    │              │              │
                                    └──────────────┼──────────────┘
                                                   ↓
                                                 交付
                                                   │
                                                   ↓
                                                 售后
```

### 业务能力图
它和业务架构不完全一样。

业务架构是：
> 企业做什么？
业务能力地图进一步回答：
> 企业具备什么能力？能力强不强？数字化支撑怎么样？

例如：
```
订单管理
├── 客户管理
├── 报价管理
├── 合同管理
├── 订单管理
└── 交付管理

生产管理
├── 生产计划
├── 排产
├── 工单管理
├── 现场报工
└── 生产追踪
```

## 流程图
### 业务流程图
用于表示一个业务端到端的流程图。比如：接到一个单后，整个流程是怎么运转的。
```
客户
 ↓
销售订单
 ↓
订单评审
 ↓
生产计划
 ↓
物料需求
 ↓
采购
 ↓
来料检验
 ↓
生产
 ↓
过程检验
 ↓
成品检验
 ↓
入库
 ↓
发货
 ↓
财务结算
```

### 价值链
节点通常也是业务操作，但是在线上，标明相应的指标，用于表示：
> 价值在哪里产生？浪费在哪里？等待在哪里？

例如订单的处理过程的价值链:
```
订单
 ↓ 2小时
计划
 ↓ 等待8小时
采购
 ↓ 等待3天
生产
 ↓ 等待4小时
质检
 ↓ 等待6小时
入库
```

### 数据流程图
用于回答：
> 数据怎么流动？
例如订单数据的流转：
```
销售订单
   ↓
ERP
   ↓
生产订单
   ↓
MES
   ↓
生产数据
   ↓
数据平台
   ↓
BI
   ↓
管理层决策
```

## 泳道图
泳道图也是流程图的一种，不过增加了人或角色或部门的维度。是流程图的更进一步：
> 谁负责这一步？
例如：
```
销售部       计划部       采购部       生产部       质量部       仓库
 │            │            │            │            │            │
下订单
 │
 ├──────────→订单评审
              │
              ├──────────→采购
              │                         │
              └──────────→生产计划─────→生产
                                           │
                                           ↓
                                        质检
                                           │
                                           ↓
                                                        入库
```

## 关系图
用于表示：
> 谁和谁有关

它不强调上下级，也不强调先后顺序。
它强调：
> 实体之间存在什么关系。

例如：
```
       客户
      ↙   ↘
    订单   产品
     ↓      ↓
    生产 ← BOM
     ↓
    物料
     ↓
   供应商
```
常见的有：
### 应用架构图
用于表示应用之间的关系，例如：
```
                 门户
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
     ERP          MES        CRM
      │           │           │
      └───────────┼───────────┘
                  ↓
                数据平台
```

### 系统集成架构图
节点通常是系统、应用、平台、设备；箭头表示它们之间的集成关系。
例如：
```
CRM
 │
 │ API
 ↓
ERP
 │
 │ MQ
 ↓
MES
 │
 │ OPC UA
 ↓
生产设备
```

这里：
-  CRM 是节点 
-  ERP 是节点 
-  MES 是节点 
-  设备是节点 
-  API / MQ / OPC UA 是连接方式
所以系统集成图回答的是：
> 系统之间怎么连接、数据怎么交换。

### 数据关系图
用于表示数据之间的关系，例如客户数据：
```
客户
 ↓
产品
 ↓
物料
 ↓
BOM
 ↓
供应商
 ↓
生产订单
 ↓
工单
 ↓
设备
 ↓
质量记录
```

### 网络拓扑
用于表示网络之间的关系，如：
```
互联网
   ↓
防火墙
   ↓
办公网
   ↓
服务器区
   ↓
生产网
   ↓
设备网
```

## 层级图
### 技术架构
用于表示技术实现，例如
```
前端
 ↓
API Gateway
 ↓
微服务
 ↓
数据库
 ↓
缓存
 ↓
消息队列
```
节点代表相应的层次。

### IT/OT
例如：
```
                    IT层
        ┌────────────────────────┐
        │ ERP / CRM / WMS / BI   │
        └───────────┬────────────┘
                    │
                  MES
                    │
        ┌───────────┴────────────┐
        │        OT层            │
        │ SCADA / PLC / DCS      │
        └───────────┬────────────┘
                    │
               生产设备
```

### 基础设施
相应的设施包括：
```
服务器
网络
存储
虚拟化
容器
云平台
数据库
备份
灾备
监控
```

## 时序图
可以理解为带相应时间或者阶段的流程图，如：
```
2026 Q4          2027 H1          2027 H2          2028
   │                │                │                │
   ↓                ↓                ↓                ↓

主数据治理 ────────→ ERP治理 ───────→ MES ──────────→ 数据平台
                         │                │
                         ↓                ↓
                       WMS              QMS
```
或者
```
第一阶段
基础治理
├── 组织治理
├── 物料编码
└── 客户主数据

第二阶段
业务系统
├── ERP
├── MES
└── WMS

第三阶段
数据能力
├── 数据平台
├── BI
└── 数据治理

第四阶段
智能化
├── AI预测
├── 智能排产
└── 智能决策
```
流程图关注“业务先后”。
路线图关注“建设先后 + 时间”。

## 矩阵图
用于表示两个不同维度之间的关系。
### 业务*系统图
| 业务   | ERP | MES | WMS | CRM |
| ---- | --- | --- | --- | --- |
| 销售订单 | ●   |     |     | ●   |
| 生产计划 | ●   | ●   |     |     |
| 生产执行 |     | ●   |     |     |
| 仓储   |     |     | ●   |     |


### 业务能力成熟度图
用于表示：
> 这个能力现在到底怎么样？

| 能力   | 当前状态   |
| ---- | ------ |
| 订单管理 | 🟡 一般  |
| 生产计划 | 🔴 较弱  |
| 采购管理 | 🟢 较成熟 |
| 质量管理 | 🔴 较弱  |
| 数据分析 | 🔴 很弱  |

## 甘特图
用于表示项目怎么执行：
```
                 2026                 2027
             Q1   Q2   Q3   Q4   Q1   Q2
ERP治理       ███████████
主数据             █████████████
MES                       ███████████████
数据平台                            ███████████
```
它适合：

项目计划
项目执行
任务排期
里程碑
项目依赖
资源安排

所以你说的：

“表示项目的计划执行”

## 象限图 / 坐标图
主要用于企业诊断和决策，比如：
根据系统的复杂及简单程度和业务价值的高低层次。来划分具体的系统：

```
          业务价值高
              ↑
       MES          ERP
              │
复杂 ─────────┼───────── 简单
              │
       老OA         小工具
              ↓
          业务价值低
```

或者从项目的业务价值及实施难易度来分析项目：
```
                 高价值
                   ↑
      重点建设      │     战略项目
                   │
低难度 ────────────┼──────────→ 高难度
                   │
       快速解决     │     暂缓
                   ↓
                 低价值
```
可以回答：
> “这么多问题，到底先解决哪个？”

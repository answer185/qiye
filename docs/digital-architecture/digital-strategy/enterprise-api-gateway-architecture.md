# 企业 API Gateway 架构：从服务暴露到统一治理

## 背景
大型制造业工厂，经常需要针对自己的特色业务、需求等开发各种系统。为了方便各类人员的使用场景，经常是多种终端并存，所以前后端分离，后端做服务拆分是必然的事。
这时为了统一客户端和后端服务之间的入口，还有做流量控制等，就需要引入API Gateway。

## 是什么
API Gateway 可以根据请求的 API 路径/规则，把请求转发到对应的后端服务。

比如：
```
                    ┌─ 订单服务
                    │   10.0.1.10:8001
                    │
用户/前端
    │               ├─ 库存服务
    │               │   10.0.1.11:8002
    ↓               │
API Gateway ─────────┼─ 生产服务
                    │   10.0.1.12:8003
                    │
                    └─ 用户服务
                        10.0.1.13:8004
```

前端不需要知道具体的服务地址，只需要访问：
```
https://api.company.com
```
即可。

## 价值
把所有外部 API 请求集中到一个统一入口，在进入内部业务系统之前，进行统一治理。
```
                    API Gateway
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       身份认证        权限控制       限流
          │              │              │
          └──────────────┼──────────────┘
                         ↓
                       路由
                         ↓
                  服务发现/负载均衡
                         ↓
              ┌──────────┼──────────┐
              ↓          ↓          ↓
             ERP        MES        WMS

```

## 系统的核心特性
### Dashboard
一般会显示相应的API数量、服务数量、服务健康状态等情况，如：
```
┌─────────────────────────────────────────────────┐
│ API Gateway                                     │
├────────────┬────────────┬────────────┬─────────┤
│ API数量    │ 服务数量   │ 请求/分钟  │ 错误率  │
│ 42         │ 8          │ 12,840     │ 0.18%   │
├────────────┴────────────┴────────────┴─────────┤
│                                                 │
│ API Traffic                                     │
│      ╭────╮                                     │
│  ╭───╯    ╰────╮                                │
│ ─────────────────────────                       │
│                                                 │
├─────────────────────────────────────────────────┤
│ 服务健康状态                                    │
│                                                 │
│ ERP      ● Healthy      12ms                    │
│ MES      ● Healthy      18ms                    │
│ WMS      ● Healthy      23ms                    │
│ QMS      ● Healthy      15ms                    │
└─────────────────────────────────────────────────┘

```

### Route
这是最核心的地方，用于设置路由及对应的服务关系。
比如：
```
Route
────────────────────────────

基本信息

Name
order-query

Path
/api/orders/{id}

Method
GET

Service
ERP

Timeout
5000 ms

Status
Enabled
```

### Service
设置相应的服务信息，如名称，通信方式，健康检测方式等。
比如：
```
ERP Order Service

Protocol:
HTTP

Host:
erp-service

Port:
8080

Health Check:
/health
```

### Upsteam
服务对应的地址，这个地址可以有多个。

比如：
```
Upstream: erp-order

Load Balancing:
Round Robin

Targets:

10.0.1.10:8080   Weight 100   ● Healthy
10.0.1.11:8080   Weight 100   ● Healthy
10.0.1.12:8080   Weight 100   ● Healthy
```

与上面二者的关系是：
> API Gateway → Route → Service → Upsteam → 负载均衡 → Target

### Consumers
谁在调用我的 API？

即设置相应的终端名称。及其允许调用的APIs

### Plugins
网关经常还会有其他的特性，如：
```
限流
认证
日志
CORS
IP限制
```
这里不需要全部硬编码在 Route 里，而应该设计成插件。

可以针对相应的路由，设置相应的运行插件。

### Logs
记录请求日志的模块。

## 自己开发 VS 第三方
在真实的场景中，不建议自己开发。因为看起来简单，实际上生产环境还会有其他问题，比如：
-  HTTPS / TLS 
-  JWT / OAuth2 / API Key 
-  限流 
-  黑白名单 
-  CORS 
-  WebSocket 
-  gRPC 
-  负载均衡 
-  健康检查 
-  熔断 
-  重试 
-  灰度发布 
-  API 版本管理 
-  日志 
-  监控 
-  高可用 
-  集群 
-  配置同步 
-  权限管理 
-  安全漏洞修复 

自己做，通常意味着，这此都是你自己的责任，而对工厂的IT部门来说，这不是核心业务能力。

## 并不是所有系统都要走Gateway
工厂的网络，系统通常都比较复杂，并不是所有的系统都要走Gateway，比如：
```
MES → PLC
MES → SCADA
MES → OPC UA
```
工业现场通信，如果走网关，反而会搞复杂了。

Gateway更适合：
```
Web
App
钉钉
供应商系统
客户门户
第三方平台
集团系统
内部微服务
        ↓
    API Gateway
```

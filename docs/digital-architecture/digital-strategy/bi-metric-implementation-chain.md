# 从业务问题到决策行动：BI 指标的完整实现链路

## 背景
决策者在遇到某些问题时，经常需要基于实际的情况出发才能做出合适的决策。这些情况大部分也是可以量化的，他们最关心不是那些明细的数据，而是汇总后，根据一定算法计算出的数值。这也是BI系统存在的意义。

这个实现过程，可以按以下链路走：

**业务问题 → 指标 → 指标口径 → 算法 → 数据来源 → 数据加工 → 指标计算 → BI展示 → 决策/行动**

## 业务层
### 业务问题
BI系统各指标的产生，并不是一上来就有的，它们的背后通常对应着相应的业务问题。比如老板问：
- 最近为什么订单交付越来越慢？
- 哪个工厂的订单交付最准时？
基于这些问题，才会有：
- 订单准时交付率
- 平均交付周期
- 订单延期率
- 各厂延期订单数
等指标。
即：
> 业务问题 → 管理决策 → 需要什么指标

### 指标
当了解清楚业务问题及管理决策需要后，就可以确定需要什么样的指标。这里需要给指标一个具体的定义，方便内部交流。比如上面的
- 订单准时交付率
可以是OTD（On-Time Delivery）

可以定义:
> 按承诺交期按时完成的订单数 ÷ 到期订单总数

### 确定指标口径
这是最重要的层次，这里需要对相关的概念做下明确的定义，比如上面的按时。

什么叫按时？如果没有具体的定义，可以会有几种不同的理解，比如：
-  实际出货日期 ≤ 承诺交期？ 
-  实际入库日期 ≤ 承诺交期？ 
-  客户签收日期 ≤ 承诺交期？ 

还有什么叫订单？
- 销售订单？
- 样品订单？
- 零食订单？
- 已取消的订单？
等。

当给出具体的定义后，需要沉淀到数的架构文档里。


### 确定指标算法
这里的算法，并不是项目代码里的各种SQL及最终的统计，而是在业务层面数据上的定义。比如上面的OTD:
```
OTD = OnTimeOrderLines / DueOrderLines
```
即按时配送的订单数 / 所有的到期的订单数

## 技术实现层
### 确定数据怎么来
如果是一个工厂，一个系统，那数据来源会简单。如果有多个系统，且考虑开发专门的数据平台，那来源过程可能会是以下的流程：
```
各工厂系统的数据->RAW(原始数据汇总层)->ODS（数据标准化层）->DWD（集团化层，增加相应的集团数据标识及主数据标识，进一步统一数据）-> DWS（各种不同维度的数据计算缓存）->BI
```
比如上面的OTD所需要的数据：
```
销售订单
    ↓
订单号
订单行
产品
数量
客户
工厂
承诺交期
    ↓
出货数据
    ↓
实际出货日期
```

然后要经常上面的几个过程处理，直到ODS层

### 指标计算
#### 明细数据层
即上面的DWD层。保存相应的明细数据，比如：
```
dwd_sales_order
dwd_sales_order_item
dwd_delivery
dwd_production_order
```
还是以业务数据的结构形态保存

#### 指标汇总层
即：DWS
```
dws_order_delivery_daily
dws_factory_delivery_monthly
dws_product_delivery_monthly
```
可以是以天、工厂、产品等不同的维度，来对DWD层的数据，进行统计缓存。

比如以定时任务的形式，对DWD的数据，按照指标算法进行聚合

```
DWD
 ↓
指标计算任务
 ↓
DWS
 ↓
BI
```

### BI展示
根据查询条件，从DWS里汇总相应的数据，并展示。比如
```
                 订单交付率 94.2%
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
     中国工厂        越南工厂        印尼工厂
      96.5%           91.2%           93.1%
       │
       ↓
   延期订单 128
       │
       ↓
   延期原因分析
       │
 ┌─────┼─────┐
 ↓     ↓     ↓
缺料   产能   质量
```

查询交互上，可以有时间维度、工厂维度，产品维度等查询。

也可以点击数字，往下钻取，展示更详情的数据，直到具体是哪些订单有问题。

## 决策/行动
决策才可以根据数据异常或提前的预警，通知相应的负责人，并做相应的业务处理。
```
BI分析
  ↓
发现异常
  ↓
触发预警
  ↓
通知负责人
  ↓
进入业务处理
```
